Guide

How to use Cents, what is available today, and the technologies and techniques used to power it.

Getting started

  1. Sign in or register from the authentication screens.
  2. Use the left sidebar to navigate between product sections.
  3. Use the right chat panel for conversation history, new conversations, and live chat replies.
  4. Open Documents to upload and review ingested content.
  5. Open Agents to manage templates and author new versions.

Current capabilities

Cents is split across three services: the Angular frontend, the FastAPI backend, and a dedicated LLM gateway. Together they support the end-to-end workflows below.

  • Authentication and session protection — sign in/register, route guards, and automatic auth headers on API calls.
  • Conversation workflow — create, rename, delete, and switch conversations from the chat panel history.
  • Streaming chat responses — assistant replies stream live using server-sent events (SSE).
  • Document ingestion — upload files and review ingested document records.
  • Tool management — create, edit, enable or disable, filter, and delete tools used for retrieval and execution.
  • Agent management — list agent templates, inspect version history, toggle enabled state, and delete templates.
  • Agent template authoring — describe a sub-agent in readable text, review or adjust the equivalent visual graph, configure Action steps as HTTP or tool calls, validate it, and save versioned updates.
  • Model gateway features — generation and embeddings are routed through a model-catalog-driven LLM service.

Workspace layout

  • Left sidebar — navigation between the app sections. Collapse it with the chevron in its header.
  • Page area — the section you selected. It takes whatever width the sidebar and chat panel leave, so widening the chat shrinks the page.
  • Chat panel — always available on the right. Collapse it with the chevron in its header; reopen it from the vertical Chat rail.
  • Resizing — drag the vertical dividers to resize the sidebar, the chat panel and the conversation history. Handles are keyboard accessible with the left and right arrow keys.
  • Persistence — every collapse state and panel width is stored in your browser, so the layout is the same after a reload.

Sections

  • Documents — upload files and review everything that has been ingested.
  • Tools — register tools, edit descriptions and executable code, test-run code, enable or disable retrieval, and delete tools.
  • Agents — review template validity/enabled state/version history, create new templates, and edit existing templates as new versions.
  • Knowledge Base — frontend page is not available yet.

Conversations and chat

  1. Open the chat panel on the right side.
  2. Press History to select an existing conversation or New to create one.
  3. Type a message and submit to send it.
  4. Assistant output streams live in the chat window using SSE.
  5. Rename or delete conversations from history when needed.

Documents workflow

  1. Open Documents in the sidebar.
  2. Upload a document from your local machine.
  3. Watch upload progress and status.
  4. Review the list of ingested document records and timestamps.

Agents workflow

  1. Open Agents from the sidebar.
  2. Review each template's latest version, validity state, and enabled state.
  3. Use View history to inspect version history for a template.
  4. Use Enable or Disable to control active versions (invalid templates cannot be enabled).
  5. Use Delete to remove a template and all versions after confirmation.
  6. Select New agent to create a template, or Edit template on a row to create a new version from the latest saved template.
  7. In Natural Language, write the complete workflow and select Build graph.
  8. Open Visual Graph to review the equivalent components and routes. A synchronized natural-language mirror is shown under the canvas.
  9. Drag a component's Connect button onto another component to create or replace its main route.
  10. Use the smaller route handles when connecting a failure path or a particular condition branch.
  11. Single-click and drag components to arrange them. Double-click a component to edit its details.
  12. For Action components, choose HTTP service or Registered tool. Tool mode accepts tool name/id and tool input JSON; HTTP mode accepts method, URL, headers/body JSON, and timeout.
  13. Use Validate to run backend schema and graph checks; fix any returned validation errors.
  14. Save after validation to create a new version without overwriting prior history.
  15. When editing, compare your draft with the latest saved template in the read-only side-by-side panel.

Agent descriptions matter at runtime. The chat orchestrator uses enabled agent descriptions to decide when a sub-agent should handle a request.

How routing is chosen

  1. The orchestrator first checks whether your message directly names an enabled sub-agent.
  2. If not, it compares your message with enabled sub-agent descriptions using semantic embeddings.
  3. If semantic ranking is unavailable, it falls back to lexical overlap.
  4. When a sub-agent is selected and completes successfully, its response is returned directly.
  5. When no sub-agent is selected, Cents uses the default route (tool retrieval, document retrieval, or direct generation).

Tool retrieval and document retrieval are semantic. Disabled tools are excluded from retrieval, so only enabled tools can be selected during execution.

Writing a sub-agent

A sub-agent is a saved, step-by-step job for Cents. It receives a user's message, follows the routes you define, keeps useful results in temporary workflow state, and returns a final response. It only runs the steps on the route selected for that request.

How a sub-agent runs

  1. The entry step receives the user's message.
  2. A listening step can extract useful details such as an account ID, date, or requested amount.
  3. Conditions choose a route using those details.
  4. Action steps can run HTTP calls or registered tools to look up or change information outside Cents.
  5. An interrupt can pause the workflow, ask the user a question, and continue with the answer.
  6. A thinking step can ask a language model to analyze the available information or write content.
  7. A reply step returns the result and ends that route.

Workflow state is the sub-agent's short-term working memory for one run. It carries parsed values, tool results, and saved model outputs from one step to the next. It is not the model's permanent memory.

When language models are called

An LLM, or large language model, is the model that understands instructions and generates text. Sub-agent authoring and execution use it at different times:

  • When you select Build graph, Cents sends the complete authoring document to the configured LLM gateway. One authoring call translates it into components and routes; it does not run the new sub-agent or call its tools.
  • When a run reaches @think, that step makes its own LLM call. Two thinking steps reached during one run make two separate calls.
  • When @listen uses LLM extraction, it makes a call to turn free-form text into named fields. A listening step configured for regular expressions does not call an LLM.
  • Conditions, interrupts, replies, and route changes do not make LLM calls by themselves. A tool or HTTP call contacts the named service, which is separate from an LLM call.

Model calls add processing time and may count toward provider usage. Cents sends them through the configured LLM gateway. A thinking step receives its instructions and the state values explicitly referenced in its prompt; it does not automatically receive every value in the workflow.

Parts of the authoring document

Write normal sentences in execution order. The first plain-language lines describe the job. Start structural lines with an @ directive, put the instruction after the directive, and indent work that belongs to a decision or failure route.

  • Name and purpose tell Cents what the whole sub-agent is meant to accomplish.
  • Directives such as @listen and @reply identify the kind of step to create.
  • The instruction after a directive explains what that particular step should do. Clear goals and expected results work better than vague requests.
  • Indentation shows which steps belong inside an @if, @else, or @on_failure route.
  • State references such as {{ stateReferenceExample }} insert information produced by an earlier step.
  • @start identifies the first step when it is not clear from document order.
  • @listen extracts information from the user's message.
  • @if, @else if, and @else describe decisions.
  • @call invokes an HTTP service or registered tool. Tool calls should include the tool name or id and the input values you want passed to that tool.
  • @interrupt pauses and asks the user for information before continuing.
  • @think adds a language-model step, and @reply ends a path with a response.
  • @on_failure describes recovery, while @guardrails sets workflow limits and policies.

Parts of a thinking prompt

Double-click an @think component in the visual graph to review its exact LLM settings. These settings control one model call:

  • Instructions are the task for the model. State the goal, any rules, and the desired answer format.
  • Context comes from references such as {{ stateReferenceExample }}. At run time, Cents replaces each reference with the value saved by an earlier listening, tool, interrupt, or thinking step.
  • Model type and model choose which configured language model handles the task.
  • Temperature controls variation. Lower values favor consistent answers; higher values allow more variety.
  • Maximum tokens limits how long the generated answer can be.
  • Output key is the name used to save the answer in workflow state so later steps can use it.
  • Failure route defines what happens if the model is unavailable or returns an unusable result.

For example, “Summarize the credit profile in three sentences, use only the supplied facts, and store the answer as recommendation” gives the model a task, a boundary, an output format, and a name for the result.

API-backed capabilities

  • Backend service — authentication, conversations, chat streaming, configuration, document upload/list, full tool management APIs, and agent template/run APIs.
  • LLM gateway — model discovery, text generation, and embeddings with folder-based model routing and optional API-key protection.
  • Frontend integration — browser app calls backend APIs through environment-based configuration and receives streaming responses for chat.

Technologies and techniques

  • Angular standalone architecture — component-first frontend with route guards and HTTP interceptors.
  • Signals-based state — UI state is managed with Angular signals for predictable local reactivity.
  • Server-Sent Events (SSE) — streamed chat responses are consumed incrementally for low-latency rendering.
  • JWT session pattern — authenticated requests carry bearer tokens, with unauthorized responses handled centrally.
  • FastAPI backend — async Python API layer handling auth, data, orchestration endpoints, and streaming responses.
  • LangGraph orchestration — backend graph workflows support both main chat orchestration and isolated sub-agent templates.
  • Hybrid persistence — relational data in SQLite and semantic vectors in Chroma.
  • LLM gateway abstraction — model-folder routing decouples backend logic from provider-specific model names.
